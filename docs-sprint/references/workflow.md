# 协作与交付流程

用于需要拆分任务、管理依赖和组织协作的需求。先读取当前项目规范与相关设计，文件位置与格式见[文档组织规范](documentation.md)。

## 人与主 agent

用户与主 agent 沟通目标、约束和重要取舍。主 agent 贯穿整个需求，维护当前有效的决定、任务依赖和交付基线，负责派发、接收结果、安排修复与集成。

子 agent 的疑问先交回主 agent。主 agent 根据已有决定解决；只有缺少必须由用户决定或授权的条件时，才汇总问题和建议询问用户。新决定由主 agent 同步给受影响的执行者。

跨模块的数据定义、接口和状态归属由一个明确的设计负责人统一；主 agent 可以兼任。发生约定变化时，暂停受影响的任务并更新其依据，其余工作继续。

## 阶段分工

按当前缺口分配执行者，已有产出直接复用，无需每个需求都重新经过全部阶段。

| 工作 | 派发时机与输入 | 产出与后续安排 |
|---|---|---|
| 实验 | 未知问题影响方案选择；提供问题、候选方案、环境和判断标准 | 可复现实验、结果、适用条件和未解决项；主 agent 据此推进设计或追加具体实验，不设最低轮数 |
| 设计 | 某部分需要形成方案；提供用户目标、相关代码、实验结论和已确定约束 | 用户流程、模块归属、接口约定和验收场景；负责人统一跨模块约定，安排独立审阅 |
| 定案 | 方案与证据足以支持选择 | 主 agent 汇总推荐方案，用户裁决尚未授权的重要取舍；结论写入设计文档，已确认决定不重复询问 |
| 开发 | 所需约定稳定；按下文提供任务上下文 | 实现、确定的代码版本与验证结果；原开发 agent 继续承担修复 |
| 验收 | 设计或代码形成确定版本；提供原始目标、定案依据、被审版本和验证环境 | 独立结论与证据；主 agent 安排修复或集成。验收场景可在设计期间准备 |

设计、开发和修复的产出在送交独立验收前进行消融实验：尝试移除本次变更中的抽象、包装、中间状态或额外分支，验证是否仍满足需求与接口约定；保留通过验证的删减，恢复必要结构并说明删减后破坏了什么。设计用具体场景检验删减后的方案，实现用相关测试或实际运行验证；删减项、保留理由和验证证据随产出交接，验收者据此检查必要性。

## 并行与依赖

任务拆分覆盖真实的跨模块调用链，不能只分配各模块内部实现。若两项工作没有各自可验收的结果，应合为一个交付任务；真实对接可以单列集成任务，并指定负责人。

- 约定依赖通过 `context` 引用确定版本的设计和共享定义；约定稳定并落地即可并行开发，不必等上游全部实现。仍可能被未决实验推翻的部分不视为稳定输入。
- `depends-on` 列出前置任务，启动条件在 `context` 中说明；未另行说明时等待前置任务 `done`。仅需共享定义时，依赖其定案产出，不等待整个上游实现完成。
- 集成任务可将启动条件设为“上游实现已通过独立验收，确定提交可用”。例如 C 负责 A、B 的联合验证，C 收到 A、B 的已验收提交即可启动，不等待由 C 自己负责的验证结果；A、B 尚未满足的完成条件仍须保留，不提前标记 `done`。
- 运行依赖决定何时能够完成真实集成验收。局部使用模拟数据不能证明集成通过；主 agent 明确尚待对接的任务，并安排真实链路验证。
- 并行开发使用独立工作区，派发时确认包含所需提交；Git 项目可使用 worktree。没有可用隔离能力时串行修改，仍可并行开展只读研究和验收准备。按实际文件修改和共享约定判断冲突；修改重叠时串行，或由后集成者基于更新后的基线重新验收。
- 每条跨模块流程指定集成负责人，尽早打通关键真实链路；共享定义、迁移和依赖配置的修改集中协调。同一交付基线的写入由主 agent 或指定集成者负责。

## 派发与上下文

主 agent 在交付分析中记录任务、当前执行者、工作目录、输入版本、当前阶段和下一步。子 agent 接收稳定依据的文件引用及本次具体指令，不默认复制完整父会话。

开发 agent 优先复用以保留实现上下文；验收者不得参与被验任务的开发。再次验收可以复用原验收者，但需检查修复影响和新增问题；上下文混乱或需要新视角时再更换执行者。

执行位置按当前待办调配，不永久绑定角色。验收积压时增加验收者；开发尚无稳定输入时安排实验或设计审阅。等待验收的开发者可以接其他独立任务，但验收中的代码快照保持固定，后续改动须重新验收。

以下提示词可调整措辞，任务依据、工作位置、输入版本和返回内容须明确。

### 开发派发

```text
执行任务：{任务文件}
工作目录：{绝对路径}
代码基线：{分支与提交}

依据任务中的设计文档和验收标准完成实现，并运行相关验证。
共享接口的变更交回主 agent 协调，按项目约定同步受影响的实现与验收依据。

返回：代码版本、消融实验结果、验证结果、未完成事项。
发现问题时继续处理；只有超出任务决策权或缺少外部条件时交回。
```

### 验收派发

```text
独立验收任务：{任务文件}
工作目录：{绝对路径}
被审版本：{提交或固定快照}
验收记录：{输出路径}

从任务目标和定案设计检查实现是否完整，并执行相关验证。
开发者的完成报告仅作为线索，结论以实际代码和运行证据为准。

返回 pass 或 blocked。
每个问题说明位置、触发条件、证据，以及为何影响本次交付。
本次负责验收，不直接修改被审实现。
```

### 修复派发

```text
继续任务：{任务文件}
工作目录：{绝对路径}
验收记录：{记录路径}
当前基线：{提交}

解决其中阻塞本次交付的问题，完成消融实验和相关验证后返回新的代码版本及结果。
若问题来自设计矛盾，说明矛盾及影响，交由主 agent 决定。
```

## 状态与协作

| 状态 | 含义 |
|---|---|
| `pending` | 启动所需的依赖产出尚未具备 |
| `ready` | `context` 中约定的依赖产出已具备，可以开始 |
| `in-progress` | 开发、验收或集成中 |
| `blocked` | 缺少必须由用户决定、授权或外部提供的条件，当前授权内无法自行解决；记录所需条件与恢复方式 |
| `done` | 验收通过，已进入本次交付基线且集成验证通过 |

交付基线采用本次需求的目标分支，不固定为 `main`。只清理本次协作创建、成果已保留且无未提交修改的工作区；恢复任务时核对实际代码和验证结果，不凭任务文件缺失或状态标签删除工作区。

## 开发与验收循环

```text
开发 -> 独立验收 -> 通过 -> 集成验证 -> 完成
          |                   |
          +-- 未通过 -> 开发修复 <- 未通过
                        |
                        +-> 再次独立验收
```

主 agent 持续执行以下调度，不在派发后结束，也不因一个任务失败而等待全部任务：

1. 找出满足启动条件的任务，分配空闲执行位置。
2. 开发返回确定版本后，立即安排独立验收。
3. 验收返回 `blocked` 时，把问题与证据交回原开发者修复，再安排验收；任务仍为 `in-progress`。
4. 验收返回 `pass` 时安排集成，并按各后续任务在 `context` 中约定的启动条件释放任务。
5. 集成失败时派发具体修复，再次进入验收；受影响的任务等待，其他任务继续推进。
6. 有任务运行时等待结果并继续调度。只有全部目标交付，或剩余工作确实受外部条件阻塞时，才结束本轮工作。

发现新的阻塞问题时继续循环。不得以“主要功能已完成”为由停止，或将本次目标内未解决的问题降为非阻塞、移入待办。只有满足任务状态 `blocked` 的外部条件时才暂停受影响任务，并继续其他可推进工作。

验收结论为 `pass` 或 `blocked`。记录问题的严重程度、是否阻塞、设计与代码位置及验证证据。违反已确认的接口约定、缺少必需能力、真实对接仍由占位实现替代，或验收未通过，均阻塞交付。

验收记录的保存与结果回写遵循[记录与维护](documentation.md#记录与维护)。

集成到交付基线后，按影响范围运行集成与回归验证；其他改动影响此前结论时，重新验证对应关系。只有目标完整实现、独立验收通过且集成验证通过，才能标记 `done`。跨模块任务必须验证真实调用链，测试边界以当前项目约定为准。
