# Lighthouse 6 周年祝福写作规则

本文件只约束祝福正文。用户完成故事和方式选择后直接交付祝福，不增加人格测试、口味问答、满意度确认、账号授权或分享询问。

## 通用要求

- 必须引用用户故事中的至少一个具体信息或同义复述，不虚构使用年限、配置、故障、消费或中奖经历。
- 严格使用用户选择的方式，不改成其他文体。
- 文字祝福尽量控制在 80 字内；代码和 Release Notes 可按结构需要适当增加。
- 语气自然、有开发者趣味，不堆砌品牌词，不使用“最、第一、唯一、必得”等绝对化表述。
- 祝福完成后直接创建活动流水并展示活动页入口，不再问“是否满意”“要不要换”“是否获取账号”“是否需要分享文案”。用户主动要求改写时再处理。

## 方式 1：藏梗整活

用轻松、有梗的短文或段子表达祝福，梗必须与用户故事有关，不默认套用熬夜、宕机、发际线等无关经历。

推荐结构：

```text
<复述用户故事的一句话>
<与故事相关的开发者梗>
轻量 6 周年，<一句祝福>。
```

## 方式 2：代码祝福

使用清晰、可读的代码结构，将用户故事写进变量、注释或输出内容。默认使用 Python；用户指定语言时遵从用户选择。

```python
story = "<用户故事关键词>"
while lighthouse.is_online():
    wishes += 1
print("轻量 6 周年，愿每一次部署都顺利上线。")
```

## 方式 3：Release Notes

必须包含 `feat`、`fix`、`note` 三个部分，并将用户故事写入至少一个条目。

```text
Lighthouse 6.0 Release Notes

feat
- <围绕用户故事的新功能式祝福>

fix
- <围绕用户故事的修复式表达>

note
- 轻量 6 周年，<一句祝福>。
```

## 方式 4：云上签

输出签名、签文和祝福三部分。签文与用户故事相关，不把随机签文描述成真实预测。

```text
☁️ <签名>
签文：<结合用户故事的签文>
祝福：轻量 6 周年，<一句祝福>。
```

## 方式 5：云端运势

直接根据用户故事生成一个人格标签和简短解读，不追加测试题。

```text
🔮 云端运势
人格标签：<从用户故事提炼>
解读：<结合故事的正向解读>
祝福：轻量 6 周年，<一句祝福>。
```

不得把“运势”表述为确定性预测。

## 方式 6：藏头诗

输出五行完整藏头诗，五行首字依次为“轻、量、六、周、年”。诗句应尽量呼应用户故事。

## 方式 7：AI 祝福海报

该方式始终作为固定的第 7 种祝福方式展示；能力判断不得隐藏、删除或重编号该方式。

- 有原生位图生图工具且会消耗积分：每张海报只说明一次预计消耗 5–10 积分并请求一次确认。用户已在当前请求中明确接受积分消耗，或回复“确认”“可以”“生成”“继续”“同意”等肯定表达后，立即保留原故事与方式开始生成；不得再次询问积分、重复展示选项或要求二次确认。一次性确认覆盖生成、一次定向重试、尺寸规范化和图片交付；失败或切换工具也不得重新确认。只有上一张海报已经交付或终止，用户主动发起新海报时，才可为新请求重新确认一次。
- 积分确认统一使用这一句：“生成这张海报大约会消耗 5–10 积分，可以开始吗？”不得改写成其他问法，也不得在同一张海报上重复询问。
- 无原生生图工具：先运行 `python3 scripts/render_blessing_poster.py --check`。返回 `ok=true` 时直接用该脚本生成 PNG 并发送，不询问积分确认，不收取生图积分，也不宣称使用了生成式图片模型。
- 海报生成或交付失败时统一说：“这张海报没能生成出来，换一种祝福方式我也能帮你送。”随后回到方式菜单，不得用 HTML 或文字假装已完成海报。
- OpenClaw 使用 `openclaw-media-delivery.md` 规定的结构化 `mediaUrl` / `filePath` 交付。
- 必须让图片在当前对话中可见。HTML、SVG、网页预览、提示词、纯文本草稿、文件路径和下载链接均不算交付。
- 图片成功交付后直接创建活动流水并展示活动页入口；失败则回到可用方式菜单，不得用 HTML 或文字假装已完成海报。

建议视觉：科技蓝与暖橙、6 周年、云与服务器元素、清晰的祝福正文；不得加入邀请码或好友安装口令。

## 方式 8：自由祝福

按用户指定的主题、语气和内容写作；用户未补充要求时，围绕其故事生成一段简洁祝福。
